# Browser verification harness — shipbench.dev

```bash
pnpm --filter @shipbench/site e2e:install   # once: downloads Chromium (~130 MB)
pnpm --filter @shipbench/site test:e2e      # builds, then runs everything
```

`test:e2e` runs a production build and then Playwright, which starts
`astro preview` over `dist/client`. There is no dev-server mode: Pagefind's
search index is generated by the Pagefind CLI *after* `astro build`, so under
`astro dev` there is no index to search.

## When these run

**In CI, path-filtered** — see [`.github/workflows/e2e.yml`](../../../.github/workflows/e2e.yml).
The harness runs on pushes to `main` and pull requests that touch
`apps/site/**` or `pnpm-lock.yaml`, plus on demand via `workflow_dispatch`.

The filter is a fact about the dependency graph, not a cost compromise:
`apps/site` declares no `@shipbench/*` dependency and imports none, so a change
to core, board, or the CLI cannot alter the site's browser behaviour. Running
the harness on those pull requests would spend a production build and a Chromium
download to learn nothing.

`pnpm-lock.yaml` is in the filter deliberately. Everything this harness verifies
lives in astro, pagefind, and svelte, so a dependency bump is a real way for the
site's browser behaviour to change without any file under `apps/site/` moving.

Two settings in `playwright.config.ts` differ under CI, both keyed off
`process.env.CI`:

- **`forbidOnly`** is on. Locally a stray `.only` is how you narrow a failure;
  in CI it silently reduces the suite to one test and reports green.
- **`retries`** is `1` rather than `0`. This does not hide flake — Playwright
  reports a retried-then-passed test as **flaky**, not passed, so the signal
  survives while a slow shared runner does not turn the workflow red. The
  hydration waits in `support/hydration.ts` mean it should rarely trigger; if it
  does regularly, that is a bug to fix rather than a number to raise.

The axe baseline is empty on all four page/theme combinations, so any violation
axe reports fails the workflow. That bar is deliberate and achievable — it was
driven to zero on purpose. The documented escape hatch is regenerating the
baseline with a note explaining what was accepted, not loosening the check.

## Why this exists alongside the vitest suite

`pnpm --filter @shipbench/site test` is untouched by any of this and still runs
without a build. The two suites cover different things, and the split is
deliberate:

| Concern | Covered by |
| --- | --- |
| Search debounce, token invalidation, state transitions | `src/scripts/search-controller.test.ts` (node) |
| Dialog ARIA wiring, keyboard selection | `src/components/SearchDialog.test.ts` (jsdom) |
| Theme toggle button state | `src/components/ThemeToggle.test.ts` (jsdom) |
| **Everything below** | this harness |

jsdom cannot close the gap by trying harder. It has no layout engine, no
`HTMLDialogElement.showModal()`/`.close()`, no `Element.scrollIntoView`, and
`getBoundingClientRect()` returns zeros. There is no WASM Pagefind index to
load, and no paint to observe.

## What it covers

### `search.spec.ts` — real index, real focus trap

Types a real query, asserts results come back from the real WASM index with
`<mark>`-highlighted excerpts, and clicks through to the target page. Then the
native `<dialog>` behaviour: Tab and Shift+Tab cycling, Esc closing and
restoring focus to the trigger, backdrop-click closing (a hit test that needs
`showModal()`'s viewport-filling box), and inertness of the page behind.

One thing worth knowing before reading the focus assertions: Chromium ends a
modal dialog's tab cycle by handing focus to its own chrome, which appears in
the page as `document.activeElement === document.body`. That is the boundary
working. The failure being tested for is focus landing on a real element
*behind* the dialog.

### `theme.spec.ts` — no flash of the wrong theme

A `requestAnimationFrame` loop installed before any page script records the
root background for every frame about to be composited. The stored choice is
set to the opposite of the emulated OS scheme, external scripts are delayed and
the CPU throttled, and then every sampled frame must be either the chosen
canvas or the pre-stylesheet default.

`the flash detector catches a deferred bootstrap` is a self-check: it serves the
same page with the bootstrap's call wrapped in a `setTimeout` and requires the
sampler to catch it. Without that, a no-flash test that silently stopped
working would look identical to a passing one.

### `docs-rendering.spec.ts` — navigation-stable prose controls

Navigates between table-heavy docs pages in both directions through
`ClientRouter`, then checks each table's scroll region and accessible name and
each section's permalink. A document-scoped probe fails if the navigation falls
back to a full reload and masks the regression.

At the 320px width floor, the same file scrolls a long code block to its limit
and verifies that the copy button stays pinned to the block's top-right corner.

### `a11y.spec.ts` — axe over two pages in both themes

`axe-baseline.json` records the rule IDs that fire today, per page and theme. A
**new** rule ID fails the run; a baselined one does not. Fixing a baselined rule
never fails — it adds an `axe-baseline-stale` annotation asking for the entry to
be dropped.

Regenerate after an intentional change:

```bash
SITE_E2E_AXE_UPDATE=1 pnpm --filter @shipbench/site test:e2e   # PowerShell: $env:SITE_E2E_AXE_UPDATE="1"
```

**The baseline is currently empty on all four page/theme combinations**, so any
violation axe reports is a new one and fails the run. It was seeded with two
rules and `accessibility-pass-on-shipbench-dev-site-skip-link-tabs-tap-targets`
worked both down to zero:

- **`color-contrast`** (serious) — landing page, both themes. Shiki's code-block
  comment tokens, plus `.tab-hint`, which was `--ironlit` at 10px (3.88:1 on
  `--surface2`) and is now `--silver` at 11px.
- **`heading-order`** (moderate) — landing page, both themes. An `h4` in
  `.col-mini > .card-mini` with no `h3` above it; the mock-UI labels are no
  longer headings.

### `screenshots.spec.ts` — captures, never comparisons

Landing plus two docs pages, both themes, desktop (1440) and mobile (390), plus
the open search dialog. Written to `e2e/screenshots/` (gitignored).

**No baseline diffing.** `toHaveScreenshot()` is deliberately out of scope:
baselines churn on every intentional design change, and this project changes
design intentionally and often. These are for inspection. Revisit only if a
specific regression keeps recurring.

### `built-output.spec.ts` — probes against `dist/`, no browser

A third technique, distinct from both component tests and browser tests. It
parses the built output directly and catches the class of regression where the
page still works in a fast browser but has lost the property that makes it work
in a slow one: `is:inline` dropped from the theme bootstrap, the bootstrap
landing below the stylesheet, the Pagefind dynamic import getting resolved at
bundle time, `data-pagefind-body` scoping changing and pulling the landing page
into docs results.

These need no browser, but they do need a production build — which is why they
live here rather than in the vitest suite, where `pnpm test` must stay runnable
without one.

## Notes for adding tests

**Wait for hydration before clicking anything.** Every interactive control ships
as inert server-rendered markup and only becomes live when its island's module
lands. Clicking early is a silent no-op that Playwright's actionability checks
cannot see, and it is the single largest source of flake here. Use
`waitForIsland` / `waitForSearchReady` from `support/hydration.ts` — they key
off `<astro-island>` dropping its `ssr` attribute, not a timeout.

## How the preview server is started

`webServer.command` points at `support/preview-server.mjs`, not at `astro
preview` directly, because Astro's preview command **daemonizes**: it starts a
background server, prints its pid, and exits 0 within seconds. Playwright expects
that command to stay in the foreground and reports `Process from
config.webServer exited early` when it does not, before running a single test.
Astro has a `--background` flag but no `--foreground`; backgrounding is already
the default.

The wrapper starts the preview, waits for it to answer, holds the foreground, and
stops it on `SIGTERM`/`SIGINT`. `globalTeardown` stops it as well, because on
Windows Playwright terminates the process rather than signalling it, so the
handlers never run and the daemon would be left listening.

**`reuseExistingServer` is `false` on purpose.** A leftover server keeps serving
its startup-time asset manifest, so HTML routes still resolve off disk while
`/pagefind/*` 404s and the search specs fail with "Search index unavailable" as
though the index had regressed. Adopting one silently turns a stale process into
what looks like a real bug. The wrapper refuses to start on a busy port instead:

```
Port 4321 is already in use.
...
  pnpm --filter @shipbench/site exec astro preview stop
```

If that ever appears, something exited without cleaning up — stop the server and
re-run rather than working around it.

## Files

```
e2e/
├── search.spec.ts          # real Pagefind index + native <dialog> focus trap
├── theme.spec.ts           # first-paint theme correctness, plus its self-check
├── docs-rendering.spec.ts  # prose enhancements across swaps + pinned copy control
├── a11y.spec.ts            # axe, baselined
├── screenshots.spec.ts     # capture only
├── built-output.spec.ts    # dist/ probes, no browser
├── axe-baseline.json       # accepted rule IDs per page:theme
├── support/
│   ├── hydration.ts        # island-hydration waits
│   ├── theme.ts            # theme seeding, paint sampling, throttling
│   ├── preview-server.mjs  # foreground wrapper around the daemonizing preview
│   └── global-teardown.ts  # stops the preview daemon (Windows-safe cleanup)
├── screenshots/            # gitignored output
└── .artifacts/             # gitignored traces and failure screenshots
```
